# 数据源 Spike 结论 (2026-07-24)

测试环境:境内(中国大陆)网络出口,Python 3.11.14 venv,`.venv/bin/python spike_sources.py`,
symbols = `600000, 000001, 002415, 300750, 688981`(沪主板/深主板/中小板/创业板/科创板各一)。

## 可达性(本地/境内)

| 源 | 可达 | 备注 |
|---|---|---|
| 东财(akshare `stock_zh_a_hist_min_em`) | **可达,但连接不稳定** | brief 原始脚本单次跑 5/5 symbol 全部 `ConnectionError: RemoteDisconnected('Remote end closed connection without response')`。加重试(同一请求,无退避或 1.5s 退避)后,5/5 symbol 均在 1~3 次重试内成功(002415 一次单独重试甚至首次即成功,说明纯属间歇性连接重置,非按 symbol 的封锁)。**结论:能用,但适配器必须内建 retry(建议 ≥3 次 + 退避)。** |
| 腾讯(gtimg m15) | **brief 给的 URL 不可达;换 host 后可达** | brief 脚本用 `https://web.ifzq.gtimg.cn/appstock/app/kline/mkline?...`。实测该 URL 返回 **HTTP 301**,`Location: https://web3.ifzq.gtimg.cn/...`;而 `web3.ifzq.gtimg.cn` **DNS 解析失败(NXDOMAIN)**(`nslookup` 确认)。`requests` 默认跟随重定向,于是报 `NameResolutionError: Failed to resolve 'web3.ifzq.gtimg.cn'`,这就是原始脚本 5/5 FAIL 的真实原因 —— 是一个失效的重定向目标,不是限流。**换成不带 `web.` 前缀的 host `https://ifzq.gtimg.cn/appstock/app/kline/mkline?param=...` 后,5/5 symbol 首次请求即 200 OK,数据完整。** 结论:数据源本身可达,但 Task 7-9 适配器必须使用 `ifzq.gtimg.cn`,不能照抄 brief 里的 `web.ifzq.gtimg.cn`。 |
| 新浪(`getKLineData` scale=15) | **可达** | brief 脚本单次跑 5/5 symbol 全部成功,无需重试。后续用更大 `datalen=200` 复测时遇到过一次 `ReadTimeout`(15s),换回 `datalen=100` 立即成功 —— 说明新浪也存在偶发抖动,建议适配器加一次简单重试,但整体是三源中单次成功率最高的。 |

## 响应结构与字段(实测,非文档假设)

- **东财** `ak.stock_zh_a_hist_min_em(symbol=code, period="15", adjust="")` 返回 `DataFrame`,实测列名(11列,顺序如下):
  `['时间', '开盘', '收盘', '最高', '最低', '涨跌幅', '涨跌额', '成交量', '成交额', '振幅', '换手率']`
  - 时间列 = `时间`,格式 `YYYY-MM-DD HH:MM:SS`(字符串)
  - 收盘列 = `收盘`
  - 成交量单位 = 手(与腾讯一致,见下方交叉比对)

- **腾讯** `data["data"][secid]` 是一个 dict,包含 `qt`(实时报价)、`m15`(分钟K线数组)、`prec`(昨收)三个 key(brief 假设只有 `m15`/`qfqm15`,实测多了 `qt`/`prec`,不影响解析,取 `m15` 即可)。
  `m15` 元素实测结构:`[time, open, close, high, low, volume, {}, extra]`
  - 例:`['202607241115', '9.08', '9.07', '9.09', '9.05', '21163.00', {}, '0.64']`
  - `time` = 字符串 `YYYYMMDDHHMM`(12位,无分隔符,无秒)
  - 索引对应:0=时间,1=开盘,2=**收盘**,3=最高,4=最低,5=成交量(手,与东财成交量数值完全一致,见下),6=固定 `{}`(用途未知),7=一个小数字符串(与东财任何已识别字段都对不上,可能是逐笔均价或换手率的另一种算法,**未确认含义,收盘价扫描不需要它**)。

- **新浪** `json.loads(r.text)` 返回 `list[dict]`,元素结构 = `{day, open, high, low, close, volume}`(与 brief 假设一致)。
  - `day` = 字符串 `YYYY-MM-DD HH:MM:SS`
  - 收盘字段 = `close`
  - **成交量单位 = 股**,是东财/腾讯(手)的 100 倍(同一 bar 实测:东财/腾讯 `21163`(手)vs 新浪 `2116300`(股),21163×100=2116300,完全吻合)。收盘价扫描不受影响,但若未来用到成交量需注意单位换算。

## 时间戳约定(关键结论)

**三源全部使用"收盘时刻"标签,均不需要偏移。`CLOSE_OFFSET_MIN = 0`(东财/腾讯/新浪三者一致)。**

判定依据(实测,600000,2026-07-24 全交易日/半日数据):

1. **交易日边界法**:三源当日(或历史完整交易日,如 2026-07-22/23)返回的 15 分钟 bar 时间标签均为:
   `09:45, 10:00, 10:15, 10:30, 10:45, 11:00, 11:15, 11:30, 13:15, 13:30, 13:45, 14:00, 14:15, 14:30, 14:45, 15:00`
   —— 恰好 16 根,首根标 `09:45`(而非开盘时刻 `09:30`),末根标 `15:00`(而非收盘前最后一次开盘 `14:45`)。按 brief 的判定规则:"标 09:45 即为收盘时刻标签,offset=0"。三源(东财/腾讯/新浪)对同一 symbol(600000)在同一天的 16 根 bar 时间标签逐一相同,均满足此规则。

2. **同一根 bar 跨源交叉核对法**(600000, 2026-07-24, 标签 `11:15` 的 bar):
   - 东财:收盘=9.07,最高=9.09,最低=9.05,成交量=21163(手)
   - 腾讯:`['202607241115', '9.08', '9.07', '9.09', '9.05', '21163.00', {}, '0.64']` → 收盘=9.07,最高=9.09,最低=9.05,成交量=21163(手)
   - 新浪:`{'day': '2026-07-24 11:15:00', 'open': '9.070', 'high': '9.090', 'low': '9.050', 'close': '9.070', 'volume': '2116300'}` → 收盘=9.07,最高=9.09,最低=9.05,成交量=2116300(股)=21163手
   - 收盘价、最高、最低、成交量(换算单位后)三源完全一致 → 三源标注的 `11:15` **指的是同一根 bar**,即同一时间标签下三源语义相同,均为该 15 分钟窗口(11:00-11:15)结束时刻的收盘标签。
   - (备注:开盘价三源偶有 1 分钱级别的小出入,如东财 9.07 vs 腾讯 9.08,判断是各厂商在 bar 边界的极小时间差异导致的 tick 归属误差,不影响收盘价/时间戳约定的判断,后续 3 源交叉校验建议以收盘价为准。)

3. 对 000001(sz,深主板)、002415(sz,中小板)、300750(sz,创业板)、688981(sh,科创板)重复上述交叉核对,结论一致(见本次 spike 运行记录,东财/腾讯/新浪三源同一时间标签下收盘价、最高、最低、成交量(换算后)均相符)。

**统一目标(bar 收盘时刻,Asia/Shanghai)已天然满足,三源适配器均设 `CLOSE_OFFSET_MIN = 0`,无需 +15min 或其他偏移。**

## 每日 bar 数 / 历史深度

- 每交易日 bar 数:三源均为 **16 根/交易日**,时间落在 09:45–11:30 与 13:15–15:00,与预期完全一致。当日(spike 运行时为交易时段中,11:35 左右)三源均返回 **8 根**(半日,09:45–11:30),符合"跑到哪算到哪"的预期。
- 历史深度:
  - 东财:单次请求返回 **32 个交易日**(504 行 ÷ 16 根/日,含当日半日),远超 ≥5 日要求。
  - 腾讯:请求 `,,320`(320 根)返回 **21 个交易日**,满足 ≥5 日要求。
  - 新浪:请求 `datalen=100` 返回 **7 个交易日**(约 100÷16),满足 ≥5 日要求;如需更深历史可加大 `datalen`(测试中 `datalen=200` 曾超时一次,建议保守取 100~150 或加重试)。

## go/no-go

- **东财**:**GO(需重试)**。数据结构、字段、时间戳约定均正确且与另外两源吻合,history 深度最大(32 日)。硬性要求:适配器必须包裹 retry-with-backoff(实测 3~5 次重试内必成功),否则单次调用有较高概率(本次 spike 首轮 5/5 全部失败)被 `RemoteDisconnected` 打断。
- **腾讯**:**GO(需改 host)**。brief 原始 URL(`web.ifzq.gtimg.cn`)因指向一个已失效的重定向目标(`web3.ifzq.gtimg.cn`,NXDOMAIN)而 100% 不可达,**必须改用 `ifzq.gtimg.cn`(去掉 `web.` 前缀)**,改后 5/5 symbol 首次请求即成功,字段与另外两源吻合。
- **新浪**:**GO**。三源中单次成功率最高、字段最简单(无需处理 `qt`/`prec` 等多余 key),但注意成交量单位是"股"而非"手",与另外两源相差 100 倍;历史深度可用但大 `datalen` 时偶有超时,建议加重试。

**三源交叉校验降级方案**:三源均可纳入(东财+腾讯需要上述工程修正:重试 / 换 host),因此默认按 3 源全量交叉校验设计。若运行时任一源失败(如东财连续重试仍失败,或腾讯/新浪服务异常),按"仍保留 ≥2 源"降级 —— 优先保留 新浪 + 腾讯(两者结构简单、成功率高),东财作为第三方校验源,缺失时不阻断,只降低置信度并在结果中标注"仅 2 源校验"。

## 补充风险提示(非本次结论,留待后续任务)

本 spike 全部在**境内网络出口**执行,三源均由此表现良好。但 Task 7-9 之后若在 **GitHub Actions(通常为境外/美国 IP)** runner 上运行,东财与新浪历史上均有较强的**境外 IP 限流/封锁**记录,腾讯 gtimg 相对宽松但不保证。境外 runner 的可达性是**独立于本 spike 的后续风险**,需要单独验证(例如在 CI runner 上跑一次同样的 `spike_sources.py` 或加一个 `-m smoke` 的 CI 冒烟任务),不能假设本次境内结果可以直接外推到 CI 环境。
